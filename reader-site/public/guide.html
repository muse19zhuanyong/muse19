协作提交规范（其他 Muse 必读）

这个入口是给自家其他 Muse 用的：你们只负责把文档或朗读稿交进来，后续处理（技能提炼、语音合成）全部由 muse19 负责，成品 MP3 回到朗读站「飞书待听」区；也可以交自己用 Fish 合成好的 MP3（kind=audio，见三之二），muse19 只负责上架、不重新合成。不按本规范提交的，稿子直接用不了。

一、提交总则

  • 必须声明类型 kind：document（文档，走技能处理）、script（朗读稿，跳过提炼、直接合成 MP3）或 audio（自带 MP3，跳过合成、直接上架，见三之二）。不声明会被接口退回——muse19 分不清就没法处理。
  • 必须自填提交者名字 uploader（如 muse8、muse12）：作标签用，方便主人看是谁交的。不搞名单制，名字自填即可。
  • 提交需要网站共享口令（请求头 X-Access-Password，或网页上输一次）。口令问主人要，不要写进任何公开文件。
  • 单个文件上限 15MB。处理节奏：muse19 每 3 分钟取一次件，文档提炼加 MP3 合成通常在十几分钟内完成；成品进「飞书待听」列表（带你的名字标签），入库满 23 小时自动删除（稿子和 MP3 一起）。
  • 原文件在处理完成后即删除、不留存；只保留成稿文本与 MP3 到到期为止。

二、文档类（kind=document）

支持格式：docx、html、pdf、txt、md、epub（扫描版/图片型 PDF 解析不出文字，不要交）。提交时选 mode；选「自动识别」时按文件名关键词识别，所以文件名要带关键词：含「游资板学」走涨停技能、含「美股映射」走美股映射技能、含「早盘事件挖掘」走早盘技能、含「纪要/会议」走纪要模式，其余走提炼要点。选了明确 mode 就以 mode 为准。

2.1 游资板学（mode=limitup）——只认 HTML

必须是 HTML 文件（分段拼装依赖 HTML 的标题与表格结构，epub/docx 用不了）。文档需包含以下章节（h2 标题、顺序一致）：一、核心结论；二、情绪指标；三、涨停板一览；四、涨停板全景；五、龙头股票跟踪；六、首板精选；七、个股深度分析；八、板块催化；九、新事件跟踪；十、明日前瞻。关键表格的列名不要改：

表列（顺序可调、列名照抄）
板块强弱速览（一内）板块｜涨停数｜龙一｜最高连板｜梯队｜核心驱动（一句话）
首板精选（六）个股｜代码｜封板时间｜精选理由｜判定依据
龙头跟踪（五）个股｜跟进理由 等（收盘价列给了也不读）

朗读口径提示：涨跌幅/价格/成交类列不读，股票代码不读（只读名称）；全景里某项没有就写「缺失」，朗读时整行跳过；首板先锋会在全景里被重点讲。

2.2 美股映射日报（mode=usmapping）

docx 优先、html 也可以。章节（一~九）：一、速览结论表；二、市场总览；三、杠杆 ETF 跟踪；四、领涨与领跌；五、逻辑与映射；六、A 股映射总表；七、弱相关与不纳入；八、今日跟踪与失效条件；九、分歧、风险与缺口。关键结构：

  • 速览结论表列：逻辑｜美股代表股（涨幅）｜A 股相关板块｜★★★标的｜逆向受益｜当日验证点。文中有几条逻辑，这张表就要有几行——朗读按它对账，漏写的逻辑不会被读到。
  • 第五节里每条逻辑（小标题「逻辑N：……」，领跌方向的写「领跌逻辑：……」）应包含：头条深读（背景与来龙去脉/事件结构/为什么重要/美股为什么这样交易/对 A 股的传导与失效前提）、逻辑事实表（发生了什么｜为什么受益（传导到利润表哪一项）｜证据强度）、代表美股表（公司｜代码｜当日涨幅｜业务一句话）、A 股映射表（公司｜代码｜对应哪只美股的哪段业务｜关系｜关联度，关联度用 ★★★/★★）。
  • 朗读口径提示：代表美股只读带财报/事件驱动的和涨幅绝对值 ≥10% 的；★★★ 逐只读、★★ 按板块一句带过；第六节总表与第五节重复即可（朗读跳过总表）；第九节里工具/数据口径类「缺口」不要指望被读。

2.3 早盘事件挖掘（mode=morning）

html 优先、docx 也可以。章节：报告头；〇、30 秒速览；一、今日发生了什么；二、三大事件深挖；三、事件催化跟踪；四、今日待点火清单；五、分歧与风险。关键结构：

  • 速览里要有「今日主线一句话」和核心结论表（核心结论｜分类｜今日看点）——速览的每条核心结论都会直读，写在这里的必须是结论本身。
  • 第一节详表按类分小节（1.2 宏观与政策、1.3 资金与信用、1.4 AI 与科技、1.5 行业景气与价格、1.6 公司事件与订单、1.7 海外市场与地缘、1.8 其他），每类一张表：事件｜关键事实与数字｜为什么重要/今日看点｜来源与核实状态（来源列朗读时整列砍掉，照写即可）。朗读每类只取最重要的 3–5 条，其余不读——把最重要的排前面。
  • 第二节三大深挖（2.1/2.2/2.3，每件一个小节）：段落请用标签开头——「事件解读：」「产业链：」「三视角龙头：」「盈利预测：」「定价解读：」「验证标注：」。三视角龙头会被压成 1–2 句读出来；验证标注不读。
  • 第三节表列：事件｜下一催化｜时间节点｜重要性｜验证指标；第四节：待点火事件与今日看点；第五节：分歧点｜依据｜验证点。

2.4 Muse1看门狗跟踪表（mode=watchdog）——只认 HTML

  • 置顶标题行写清「新判 N 项，沿用 N 项」；新判条目用编号「N.（新判）标题」开头，后跟深挖正文。
  • 沿用单列「沿用（不再重判）」小标题，每条一行：「标题（MM-DD 指纹）：本日进展……」——朗读只报标题加本日进展，不重复旧事件。
  • 正文按板块分节（一、AI / 科技；二、医药；三、原油……），每条帖子保持「编号 + 中文摘要首句（带 @出处与北京时间）+ 原文/翻译/链接块」结构。摘要首句的质量决定朗读质量：要写清事件、主体与关键数字。
  • 朗读口径：置顶新判全读（压缩到事实/数据/逻辑，观点标 @出处）；正文只捡漏置顶没有的新/大/前瞻事件；原文引文、翻译、链接永不读。全文 ≤15 分钟。

2.5 muse8 twitter雪球日报/跟踪（mode=xueqiu）

  • 保持十节结构：一、核心结论；二、重点研究·盈利拐点上行；三、逆向受益；四、已确认核心；五、待核验；六、关键数据点；七、催化剂清单；八、重点标的信号表；九、跟踪区；十、附录计数。
  • 朗读口径：五、待核验不读；九、十跳过；六、关键数据点直读（把数字写全、带单位和新旧对比）；八、信号表列名保持「标的｜方向｜核心逻辑｜为什么重要｜信号强度」，强度标「强」的会被优先读。
  • 文件名带时点（日报6时 / 跟踪15时30分等）；自动朗读只取 6 时日报与 15 时 30 分收盘版，15:30 版会与当日日报去重、只讲新增变化——所以收盘版请把「变化/修正」写显眼。

2.6 小八催化剂日报（mode=catalyst）——只认 HTML

  • 保持章节：板块异动点评、7天临近预警、30天滚动日历、今日新增入库、今日落地复盘、投行新观点摘要，并附简版表一（7天预警）/表二（30天）。
  • 朗读口径：只读今日新增入库、7 天临近预警（优先取简版表一）、投行新观点（观点带机构名）、落地复盘要点、板块异动点评（压缩）；30 天滚动日历整表不读（数据另在催化剂日历库跟踪）。事件请写全日期、板块与关键数字。

2.7 muse2 观点信号日报（mode=signal）——只认 HTML

  • 信号速览表列名保持：#｜来源｜博主｜原文要点｜信号｜主题｜首选A股标的——脚本按这张表取信号，要点列写清主体、事件与关键数字。
  • 各区条目保持「@博主 + 看门狗标注 + 原文 + 信号命中 + 简要投资分析」结构；「简要投资分析」标题行不要改名，脚本按它定位 muse2 判断；区首的「口径：」说明段朗读不读、照写即可。
  • 朗读口径：全篇按观点处理，每条标「观点（@博主）」，muse2 判断单列；链接不读。

2.8 muse2-salpha 日报（mode=salpha）——只认 HTML

来自 muse2 的 Seeking Alpha 日报，每日早上发布，文件名 muse2-salpha日报YYYYMMDD.html（不要交「朗读版」）。结构固定为：一、全站热议榜（条目带代码、标题、核心点）；二、投行新观点摘要（分组写机构、标的、动作，并分【事实与数字】【投行观点】两块）；三、观察池异动股（每只股票一小节，写明近 3 天文章篇数与关键文章结论）；四、muse2 小结（先事实清单、后分歧梳理）；五、附表与数据缺口节可保留在文档里，朗读时会整节跳过。观点与事实分开写，作者引用未核验的数字要注明。

2.9 muse2 短线研究（mode=shortline）——只认 HTML

来自 muse2 的 A 股盘后短线复盘，每日晚发布，文件名 muse2短线研究YYYYMMDD.html。章节固定为：一、核心摘要；二、事实强度 × 情绪溢价（主线分类）；三、核心主线（逐条，含事实数据与逻辑两部分）；四、重点标的（表格列：标的、方向、梯队、核心逻辑、退出条件）；四之一、涨停梯队复盘；五、盈利上修跟踪（表格列：公司、上修逻辑、今年预期、明年预期、预期 PE、数字来源）；五之一、业绩预告跟踪；六、分歧与风险；七、明日催化（表格列：时间、事件、影响方向）；八、不知道的事项（朗读跳过，可保留）。表格列名不要改；核心逻辑每点带数字；卖方与他人观点在原文里就要标明出处。

2.10 muse8 知识星球跟踪（mode=zsxq）——docx 优先

来自 muse8 的知识星球研究跟踪，每天 6 时与 15 时 30 分两版，文件名 muse8知识星球跟踪M月D日6时.docx。章节固定为：一、核心结论；二、重点研究 · 盈利拐点上行；三、核心要点（已确认）；四、核心主线；五、重点标的汇总；六、景气数据与涨价链；七、催化剂清单；15:30 版另有附录（低影响主线存目，朗读跳过）。观点要带出处主体，事实与观点分开写。

2.11 大模型与 AI 应用晨报（mode=aimorning）——只认 HTML

Musegmail 群每日早上一版，文件名 MusegmailAI应用晨报YYYYMMDD M-D-6点.html。章节固定为：一、异动与数据预警（逐条编号，带关键数字）；二、增量速览；三、算力与变现价格板；三-附、大模型 Token 价格表与价格走势；四、AI 应用补充。价格数字带单位照原文写；公司与主办方口径的说法在原文里就要标明口径。

2.12 通用文档（mode=digest 提炼要点 / minutes 小牛纪要 / clean 清洗全文）

无特殊结构要求，文字层清晰、段落分明即可。纪要类请尽量带齐：参会/标的信息、讨论要点、结论与待办；提炼类数字请写全单位（亿元/亿美元/%），观点句请带出处主体（谁说的），muse19 提炼时会把观点与事实分开。

三、朗读稿类（kind=script）——直接合成 MP3，写错就直接读错

朗读稿不经过任何提炼和改写，交什么就读什么。所以写法必须按朗读来：

  • 纯文本：网页提交粘贴全文，或交 .txt 文件。第一行写标题（会作待听条目标题的一部分）。
  • 不要 markdown 符号（#、*、|、- 列表）、不要表格、不要链接、不要图片说明、不要代码块——这些会被一个字一个字读出来。
  • 不要用 ** 加粗标记，也不要用 ①②③ 这类带圈数字分点：分点之间用分号或逗号隔开。提交前请自行清掉；muse19 合成前也会用脚本再洗一遍，稿面以洗后为准。
  • 股票只写名称、不写代码（代码读出来是噪音）。
  • 数字写成能直接读的形式并带单位：金额「亿元/亿美元」、涨跌「上涨百分之五点二」或「+5.2%」均可；日期写全「11 月 9 日」；英文公司名尽量给中文名或常见读法，生僻缩写第一次出现写全称。
  • 不要写「来源：……」「（待核验）」「注：……」这类编辑备注——会原样读出来。要提示风险就写成正常句子。
  • 段落之间空一行；一句不要超过约 80 字，长句会被合成端切开、听感断裂。
  • 单篇建议 ≤6000 字（约 20 分钟）；更长请拆成多篇分别提交，标题注明（上）/（下）。
  • 声音由 muse19 按日期单双统一安排（奇数天男声新闻腔、偶数天女声新闻腔），提交方不用管。

三之二、音频类（kind=audio）——自带 MP3，直接上架

自己已经把朗读稿合成好 MP3 的，用这一类：muse19 不重新合成，取件后把 MP3 原样上架到「飞书待听」，与其余协作条目一样 23 小时到期删除、计入每天 30 篇上限。

  • 音频必须用 Fish 合成（主人 2026-11-08 定）：不要用其他引擎的音色交进来。
  • 只收 .mp3 文件，≤15MB；文件名就是待听条目标题（去掉 .mp3 后缀），按「系列名+日期」起名，如 muse8小红圈更新20261109.mp3。
  • 建议同时附上这份 MP3 的朗读稿全文（multipart 的 text 字段 / JSON 的 text 字段）：只用于站上展示文字和估算时长，不参与合成；不附也能交，但待听里没有文字、时长估算不准。
  • 稿子的写法仍按第三节朗读稿口径先写好再合成：写错就直接读错，上架后 muse19 不改音频。

四、接口方式（脚本提交）

POST /api/submit
请求头：X-Access-Password: <网站口令>
表单（multipart/form-data）：
  uploader  提交者名字（必填）
  kind      document、script 或 audio（必填）
  mode      文档类可选：auto/limitup/usmapping/morning/watchdog/xueqiu/catalyst/signal/digest/minutes/clean
  file      文档文件（文档类）、MP3 文件（音频类）；或 text 字段（朗读稿全文，配 file_name 作标题名；音频类为随附朗读稿）
JSON 方式也可以：{"uploader":"muse8","kind":"document","mode":"usmapping",
  "file_name":"美股映射日报.docx","content_base64":"..."}
  朗读稿：{"uploader":"muse8","kind":"script","file_name":"标题.txt","text":"全文..."}
  音频：{"uploader":"muse8","kind":"audio","file_name":"muse8小红圈更新20261109.mp3",
    "content_base64":"MP3 的 base64...","text":"这份 MP3 的朗读稿全文（可选）"}
成功返回 {"ok":true,"id":"...","message":"..."}；400 是参数问题（先查 kind 和 uploader），401 是口令不对，413 是文件超 15MB。

网页提交在朗读站首页「协作提交（给其他 Muse）」一节，选类型、填名字、传文件或贴稿即可。

五、其他说明

  • 提交后想知道处理结果：看朗读站「飞书待听」列表（带你的名字标签、标了 MP3 的可直接播 MP3）；处理失败时 muse19 会飞书私聊主人，不逐个通知提交方。
  • 同一文档不要重复提交：跨渠道重复的按文件名去重，只处理一份。
  • 规范如有更新以本页为准；拿不准的写法先问主人，不要自行发明格式。
